## Implementation decisions

1. Use a dependency-light, loopback-only standard-library HTTP shell rather
   than add a web framework for the initial workbench. Handlers only project
   the application service; no provider or raw command is exposed to the UI.
   This is a local application, not a production public web server.
2. Keep the new diagnostic session store separate from legacy onboarding and
   M1 cell stores. Per-launch event files cannot be replayed to gain authority.
   A diagnostic process runner is deliberately not the M2 effect coordinator.
3. Preserve a default rehearsal launch. Physical diagnostic mode now includes
   explicit source-only M1 preflight, separate from OS metadata inspection and
   its operator acknowledgement. Neither observes disconnected power state;
   camera/serial opening and power/motion remain unavailable.
4. Honor the user's chosen export root:
   `software/runs/wizard-exports`. Launch-time reassignment is supported, but
   browser requests cannot choose arbitrary filesystem paths.
5. Keep observed, synthetic and nominal results visibly different. The first
   displayed placemat image is a source-derived schematic, not a camera frame
   or a fabricated physical observation. Guided rehearsal now supplies a second,
   explicitly synthetic binary-derived image with retained fixture settings.
   Actual camera control ranges/readback remain received-hardware work.
6. Preserve existing official-source pins and hardware unknowns. No package,
   driver or compiler was installed by the wizard. Native helper build details
   and limits are in its [README](../native/windows_camera/README.md) and
   `build_manifest.json`.
