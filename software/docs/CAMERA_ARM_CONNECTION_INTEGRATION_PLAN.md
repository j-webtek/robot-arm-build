## 1. What we are going to deliver

One local interface should let the operator identify the purchased camera and
arm, configure their connections, see the actual camera image, adjust supported
camera settings, complete guided calibration, and establish a verified arm
connection. It should show precisely what is connected, what has been measured,
what is still unknown, and which next action is permitted.

This is the target architecture, not a claim that every capability is delivered.
The first local diagnostic/rehearsal interface now exists; physical connection,
preview and commissioning integration remain incomplete.
Hardware-specific identities and measurements cannot be filled in until
the received devices are inspected. We can build the real provider code, UI,
workflow, tests, packaging, and rehearsals before that inspection.

The first useful delivery is a functioning camera/connection workbench in
rehearsal, with the physical adapters implemented behind explicit activation
gates. We should build and exercise the UI early, alongside the provider work,
instead of postponing every visible screen until all motion qualification is
finished.

The finished system has three deliberately separate levels:

| Level | Operator outcome | What it does not imply |
| --- | --- | --- |
| Camera setup | See the selected camera, inspect mode/controls, focus the lens, check coverage, collect calibration data | Arm power or motion permission |
| Arm commissioning | Identify the controller, supervise startup, establish a bounded feedback exchange, verify installed firmware evidence | A calibrated home position, autonomous initialization, or permission to type |
| Qualified operations console, later | Submit reviewed hover, individual keypress, or Android tap plans to a separately qualified executor | Arbitrary raw robot commands or unattended first power-on |

“Start the system” means launch the application and assess connections without
opening them. “Start the arm” means guide a supervised power/connection process;
it is not a software-controlled mains/DC power switch. “Initialize the arm”
must later mean a specifically qualified reference or park procedure, not a
generic connect-time reset or vendor demo movement.

## 3. Hardware and wiring contract

### 3.1 Connection layout

```text
                         Windows workstation
                   RoCell service + local browser
                         /                 \
       dedicated host USB 3 port          host USB data port
                    |                           |
          USB data cable                  USB data cable
                    |                           |
     Arducam B0477 on static portal      RoArm ESP32 serial USB port
                                                |
                                  controller + servo bus + arm
                                                |
                           separate approved DC supply/power cut

             Both camera geometry and robot geometry reference
                    the same measured placemat board.
```

The camera plugs into the host, not the arm's ESP32. No Raspberry Pi, CSI ribbon
cable, ESP camera firmware, or moving-arm camera holder is required for this
architecture. The portal/support remains the existing bench-anchored design;
it must maintain a measured relationship to the board.

Waveshare identifies controller port **9, USB**, as the ESP32 serial interface;
port 8 is the LiDAR interface. Its documentation also identifies a CP2102 driver
path and an external 12 V supply. The arrival screen should show the official
diagram/link and require confirmation against the actual controller revision.
USB enumeration alone does not prove servo power is present or absent.
[Waveshare RoArm-M3 hardware guide](https://www.waveshare.com/wiki/RoArm-M3)

Plan a direct USB 3 camera connection with strain relief and an adequate cable
route. A USB-C connector does not establish negotiated USB speed. The wizard
must measure topology/speed, show unavailable observations as unknown, and
identify USB2 negotiation as a native-mode qualification blocker. It must not
silently switch the production profile to a lower-resolution mode.

### 4.1 Purchased camera facts and the important optical uncertainty

The B0477 vendor specification lists IMX283, rolling shutter, manual focus,
YUY2, Windows/Linux UVC, and a nominal 16 mm C-mount lens with manual aperture.
Published USB3 modes are 1280×720/120 fps, 1920×1080/60, 2720×1536/40,
3840×2160/20 and 5472×3648/9; actual negotiated operation must be measured.
Its documented electronic controls include brightness, contrast, saturation,
white balance, gain and exposure.
[B0477 datasheet](https://blog.arducam.com/downloads/datasheet/B0477_20MP_IMX283_USB3.0_Camera_Datasheet.pdf)

The same datasheet lists a **default focus range of 5 m to infinity**. Our
approximately one-metre installation therefore needs an early physical focus
test. This does not establish the lens's complete adjustable focus range, but
we must not promise adequate focus at our board. The wizard should guide a
focus chart test at board, keytop and screen heights before final calibration.
If it fails, investigate a compatible closer-focusing lens with the vendor;
that is an optical/profile change requiring recalibration, not a software fix.

Do not display functioning autofocus or aperture sliders for this manually
adjusted lens. Show manual instructions, sharpness feedback and witness-photo
capture instead. Treat the user's purchase description as a B0477 candidate
until the actual SKU, lens, connectors and receipt are checked.

### 5.1 Responsibilities

- **UI:** explain, display, collect edits and explicit confirmations. It cannot
  produce permits, write session files, choose arbitrary executables, or open
  devices. Browser refresh and GET/status requests have no hardware effects.
- **Service:** build the canonical stage view and action preview, validate
  staged input, assess evidence, apply an exact reviewed decision, and delegate
  approved campaigns. Browser and CLI call the same application functions.
- **Coordinator:** recheck the current source/session/identity challenge under
  ordered leases, durably arm an attempt, dispatch one registered worker with
  a single-use exact campaign permit, reconcile its result, and quarantine
  ambiguity. M1 remains a storage dependency, not an effect executor.
- **Camera worker:** one identity-bound camera campaign, native negotiation,
  controls, bounded preview/capture, genuine sample metadata and cleanup.
- **Arm worker:** one identity-bound onboarding feedback campaign. No raw
  command console, motion, torque changes, boot-file changes or firmware update.
- **Evidence service:** bounded binary datasets, immutable receipts, hash-bound
  derived images, progress/health metrics and export. Live preview is not
  automatically retained calibration evidence.

Constructors and imports remain hardware-inert. Preview sessions are finite
campaigns, not camera objects stored in a global web-server variable. Worker
crash, timeout or application restart never automatically resumes an attempt.

### 5.2 Proposed module boundaries

Names are implementation targets, not files claimed to exist. Reuse equivalent
existing modules where their contracts already satisfy the responsibility.

```text
software/src/rocell/application/
  arrival_wizard_service.py          # one UI/CLI application boundary
  cell_commissioning_coordinator.py  # effects, leases, attempts, permits
  connection_assessment.py           # pure decisions/remediation
  device_binding_service.py          # candidate -> reviewed device binding
  camera_campaign_service.py        # typed camera requests/receipts
  arm_onboarding_service.py          # power evidence + one-shot feedback
software/src/rocell/providers/windows/
  camera_worker_client.py           # strict bounded native-helper IPC
  serial_onboarding_worker.py       # narrow physical serial implementation
software/native/windows_camera/
  ...                              # C++/Windows SDK helper + native tests
software/src/rocell/ui/
  server.py, templates/, static/    # presentation and transport only
software/tests/
  ...                              # service, worker, fault and UI parity tests
```

Prefer a small isolated C++ Windows SDK camera helper to broad untyped COM
calls throughout Python. A feasibility spike must demonstrate endpoint mapping,
native sample capture and control readback before this choice is finalized.
An explicit, separately qualified DirectShow backend is a contingency, never
silent runtime fallback. Linux remains a later provider implementation.

Ship a reproducibly built, versioned native executable for the supported
Windows architecture. The operator should not need a compiler, full ROS
installation or an IDE. Missing/unsupported helper means a visible unavailable
feature; rehearsal and documentation remain usable.

### 5.3 Request/result contracts

Every start request contains the cell/session ID, current-state challenge,
action kind, exact selected identity, settings/plan hash, finite budget and
one-use request key. The service returns an operation ID, progress state,
reason codes and evidence references—not a device handle.

Action previews explain what can happen before approval: camera activation,
control changes, serial-open/reset possibility, expected duration, counts,
cleanup and manual power responsibilities. Double-clicking the same request
returns the existing attempt status; it never dispatches a second physical
operation. A different request key cannot bypass an active attempt or hold.

Keep command/status IPC small and schema-validated. Put frame data in bounded
binary transfers or a small ring of owned buffers with sequence/length checks,
not JSON/base64. Validate worker identity, protocol version, size limits and
exit/cleanup accounting before accepting results. UI cancellation requests
cessation and reports what is known; it does not assert that an arm stopped.

## 6. Camera connection and control workflow

### 6.1 Discover and bind the correct unit

1. Run host/source checks without activating a capture source.
2. Ask the operator to clear private material from the camera view and confirm
   the received camera/lens/cable against the purchased profile.
3. Enumerate OS metadata. Show friendly label, VID/PID, serial if supplied,
   container/device instance IDs, endpoint path, driver and topology.
4. Guide one deliberate unplug/replug identification trial as allowed by the
   stage plan. Highlight the changed candidate, but require user selection.
5. Store a reviewed binding, not `camera_index=0`. Resolve an ephemeral capture
   locator only from this binding and recheck immediately before opening.
6. If serial is absent or nonunique, hold until a reviewed symbolic
   link/container/topology policy proves identity across reconnect and reboot.
   A labeled dedicated port may be part of that policy, not a manufactured
   serial or a guarantee that a camera moved to another port is identical.

OS inventory is metadata-only; native mode/control enumeration may require
activation and therefore belongs inside a permitted campaign. UI labels must
not disguise an open as a harmless “scan.”

### 6.2 Configure, read back and preview

The camera page needs these controls and observations:

| UI element | Behavior |
| --- | --- |
| Selected device | Physical identity and binding quality; no automatic first-device selection |
| Start preview / Stop preview | Explicit bounded campaign; countdown, current operation and cleanup status |
| Mode selector | Enumerated modes; requested vs actual width/height/fps/subtype shown together |
| Image | Board overview, optional tag overlay, center/corner focus crops and orientation reference |
| Exposure, gain, white balance | Display supported range/step/default/unit and auto/manual capability; Apply and read back |
| Other supported controls | Advanced panel; hide unsupported controls and explain unavailable readback |
| Manual focus/aperture | Guided physical adjustment, focus metric and witness marks; no pretend motor control |
| Health | Actual frame delivery, arrival age, drops, sequence discontinuities, topology/speed, stale-frame warnings |
| Snapshot / calibration capture | Explicit capture campaign/evidence target; not a screenshot of a browser-scaled preview |
| Save candidate profile | Immutable staged revision; not automatic calibration or build promotion |

For each configuration campaign: select exact identity; enumerate native
formats; request the approved format; read back the negotiated media type and
controls; settle under a bounded policy; capture; close; retain counts and
outcomes. Readback mismatch is a failed configuration, not a green checkmark.

Proposed interactive preview duration: up to five minutes per explicitly
approved campaign, subject to the reviewed worker policy. The initial campaign
has immutable settings. Applying new settings ends the old campaign and starts
a separately approved configuration/preview campaign with a visible close/open
transition. This preserves the existing self-contained worker rule. Do not
silently renew an expired preview or add a perpetual background camera service.

Likewise, an evidence snapshot requested during preview must either have been
included in that campaign's approved capture plan or wait for preview cleanup
and a separate capture campaign. The browser cannot take ownership of the
camera or turn a display-only frame into qualified evidence.

If later usability requires in-stream setting changes, first add and test a
bounded control sub-operation protocol with individual authorization and
settings-epoch transitions. Do not smuggle unreviewed writes into a status call.

### 6.3 Native imaging and efficient data handling

Use the purchased native calibration mode from the existing profile. A
convenient lower-mode live diagnostic view can be an explicit separate preset,
but cannot satisfy the native-mode stage or reuse its intrinsics automatically.
Prefer a downsampled preview derived from the same native stream while
calibrating. Identify every crop/resize/rotation by an explicit transform.

Engineering sizing from the selected profile:

- Minimum packed native YUY2 frame: `5472 × 3648 × 2 = 39,923,712` bytes.
- At 9 frames/s: approximately 359 MB/s of image payload before USB overhead.
- Thirty-two minimum raw frames: 1,277,558,784 bytes before derived images.

Real sample stride/padding can increase those figures. These calculations
explain why an unbounded Python list of full frames and the existing 32 MiB
single-item evidence limit are unsuitable. Use M3 chunked, content-addressed,
manifest-last datasets with disk preflight and quotas. Stream hashing/writes;
reuse buffers; compute sharpness/preview on bounded regions; never save every
preview frame by default. Publish a downscaled preview at at most the native
delivery rate, with backpressure and a latest-frame policy for display only.
Evidence capture must explicitly account for drops instead of silently using
the display policy.

Persist requested and observed modes separately; include subtype, stride,
sample length, orientation, device/backend identity, settings epoch, frame
index and monotonic arrival brackets. A host counter is not a sensor sequence
number. A media timestamp is not automatically exposure time. The stage's
visible time-varying challenge remains required for freshness qualification.

If hardware lacks required timing evidence, return a limitation/hold for the
affected stage; do not synthesize timestamps to pass. Different JPEG hashes or
changing exposure values alone are not proof of a fresh scene.

### 6.4 Settings and calibration invalidation

The UI stages settings before apply. Each applied campaign gets a settings
revision; configured values and actual readback are retained. Mode, crop,
orientation, focus/lens, mount or geometry changes invalidate dependent
calibration. Exposure/gain/white-balance changes require image-quality and
localization revalidation under the existing epoch policy; they must not
silently inherit unrelated acceptance evidence.

Do not repeatedly rewrite source-controlled JSON during normal camera tuning.
Keep observations/candidates in session evidence, then render an explicit
reviewed configuration successor when warranted. Source/package changes make
old source-bound sessions read-only rather than automatically repairing them.

## 7. Arm connection, startup and initialization workflow

### 7.1 Connection profile to implement

Reuse [`arm_connection.json`](../config/arm_connection.json): USB serial,
115200 baud, newline-terminated JSON, LF transmit and accepted LF/CRLF receive,
RTS/DTR false, one-second read/write timeouts, no blind retries, no automatic
connect or initialize, and a single qualified owner. Explicitly retain 8N1 and
disabled hardware/software flow control in the worker's observed settings.

Port is currently null by design. The wizard will resolve the observed COM
port from the reviewed controller identity immediately before each campaign.
Do not hard-code a guessed COM number, VID/PID, controller serial, arm serial,
or firmware version. A USB bridge identity identifies the controller interface;
the separate arm/model receipt must bind that controller to the actual Pro arm.

### 7.2 What the Arm page should show

- Received arm/model and controller identity; current ephemeral port.
- Driver status, serial profile, last identity comparison and competing-owner
  status within RoCell. Explain that local locks do not exclude another host,
  Wi-Fi client or controller-side mission.
- Power state as disconnected/observed/unknown with evidence time—not an
  inferred green indicator because Windows sees a COM port.
- Firmware identity and how it was obtained; missing/unsupported is distinct
  from a successfully parsed feedback packet.
- Last feedback fields with units, provenance, receive time and validity.
  Missing fields remain unavailable; old feedback is visibly stale.
- Separate actions: inspect connection metadata, review power setup, observe
  startup, perform one feedback test, close/finish, export diagnostics.
- Locked future functions: reference qualification, safe park, hover test,
  keyboard actions and phone actions. Each displays the missing prerequisite.

### 7.3 Supervised sequence

1. **Stage 9: identity while actuator power is disconnected.** Inspect labels,
   supply/cable and metadata only. Do not open serial to discover the model.
2. **Stage 10: power/safety review.** Check the built cell, startup swept
   volume, independent power cut, containment against gravity, operator/observer
   positions and absence of devices/contact tooling as required by the catalog.
3. **Stage 11: observed manual startup.** Arm a unique power-event attempt
   before instructing the operator to energize. Send zero host commands,
   observe once, manually de-energize and record the final state.
4. **Stage 12: new power envelope and controlled serial connection.** Recheck
   identity/ownership, authorize one campaign, manually energize under the
   reviewed ceremony, configure the unopened serial object, then open once.
5. Observe the receive buffer during the bounded quiet interval. Retain any
   unexpected bytes; do not discard boot text or stale feedback to fabricate
   a clean buffer. When the precondition fails, make no request write.
6. Only when the exact permit and quiet-buffer test pass, attempt the existing
   one-shot T=105 request. Retain raw bytes, parse under the approved firmware
   policy, account for extra/partial data, close and require de-energization.
7. Assess the report and installed firmware evidence. Display either verified
   diagnostic connection, a specific blocker, or an uncertain-effect hold.

Waveshare documents automatic middle-position movement at power-on. That is
why observing startup precedes our first serial test; it is not a calibrated
home or a guarantee of board clearance.
[Waveshare startup instructions](https://www.waveshare.com/wiki/RoArm-M3)

Serial-open is itself a possible reset/effect boundary. The first physical
connection retains the current one-request limit. No automatic reconnect,
second try, periodic polling, baud-rate probing, torque toggle or demo motion
is allowed to turn a failed handshake into a pass.

The response does not echo a host transaction ID. Preserve the existing
quiet-buffer, timing and one-outstanding-request rules; software-generated
request IDs only correlate our logs, not firmware-level acknowledgments.

### 7.4 Firmware and boot-policy evidence

T=105 telemetry is not proof of the installed firmware version, a completed
motion, or absence of autonomous boot behavior. Establish a separately
reviewed non-motion observation method for the received firmware. Possible
evidence sources include a documented version display or bounded readback
supported by that exact firmware; support must be verified before adding a
command to a worker. Do not invent a version-query command.

Keep a source pin, firmware-package hash, observed revision/evidence method,
protocol compatibility assessment and boot-policy receipt. An archived vendor
package is not evidence that the delivered controller contains those bytes.
If adequate installed identity cannot be obtained, report the hold and create
a supervised maintenance investigation—not an automatic firmware upgrade.

Inspect controller-side startup missions and alternative control paths only
through explicitly reviewed procedures. Do not change Wi-Fi/ESP-NOW, boot
files or firmware as a hidden setup step. The vendor dashboard is a separate
maintenance tool: finish/release RoCell campaigns before opening it, and
require renewed evidence after settings or firmware changes.

### 7.5 How we eventually provide startup/control from this interface

The commissioning wizard itself remains non-motion-capable, as required by
the reviewed plan. It can guide energization, connect for diagnostics, acquire
camera evidence and import reference/hover reports.

After the separate motion executor and its releases are implemented, an
Operations tab can present an exact reference/park/hover plan and hand it to
that executor through a distinct typed service. This gives the operator one
interface without giving the wizard a raw motion endpoint. The first startup
plan must be validated against measured geometry, tool configuration,
controller correlation, limits and current power/vision evidence.

During later qualified operation, bounded telemetry polling can be a declared
execution-campaign responsibility with deadlines and one outstanding request.
It is not a new Stage-12 polling loop. Reconnection or restarting the app must
invalidate execution authorization and never resume a keypress or tap.

Closing serial does not turn off servo power or guarantee stopping. A Stop
button must describe its software meaning and show the physical power-cut
instruction; it cannot be labeled a certified emergency stop. Never issue
automatic park, torque release or re-energization as error cleanup.

Stage 7 optics tests remain preliminary. Stage 8 owns installed intrinsics and

the camera/lens/support is finally secured.

### 8.3 Useful automation without surprise hardware actions

Automatically perform pure checks, fill fields from trustworthy observations,
propose a unique matching candidate, evaluate capture quality, explain failures,
prepare artifact summaries, and suggest the next eligible action. Let the
operator explicitly start capture, configuration, reconnect trials and power
ceremonies. Reviewer acceptance is separate from acquisition success.

Use plain-language reason codes with a specific next step, for example:

- `CAMERA_NOT_FOUND`: inspect data cable, selected host port and Windows access.
- `CAMERA_IDENTITY_AMBIGUOUS`: distinguish units; do not select the first match.
- `USB_LINK_UNQUALIFIED`: verify actual speed and direct cable/port topology.
- `CAMERA_MODE_READBACK_MISMATCH`: retain requested/actual values; no fallback.
- `OPTICS_NEAR_FOCUS_UNPROVEN`: perform the one-metre chart test.
- `CAMERA_FRAME_STALE`: stop using the preview/calibration result and inspect
  the failed freshness evidence; no automatic reopen.
- `ARM_IDENTITY_CHANGED`: keep port closed and repeat binding review.
- `ARM_OPEN_RESET_OR_UNEXPECTED_BYTES`: retain the capture and stop the campaign.
- `FIRMWARE_IDENTITY_UNPROVEN`: hold commissioning pending approved evidence.
- `PRIOR_EFFECT_UNCERTAIN`: enter read-only reconciliation; no automatic retry.

These names are proposed additions and must be reconciled with existing enums
instead of creating duplicate error vocabularies.

### 8.4 Local service, privacy and packaging

- Bind only to loopback. Use launch/session tokens, CSRF protection, strict
  Host/Origin checks, escaped templates, local assets and no arbitrary file
  serving. No public/LAN listener or remote-control feature in the first build.
- Keep all hardware operations behind typed POST actions and server-side
  eligibility checks. The browser cannot send serial JSON or set authority bits.
- Keep device workers independent from browser connections: closing a tab
  requests cleanup according to campaign policy, and reopening displays the
  existing operation instead of creating another one.
- Separate live preview from retained evidence. Explicitly show whether
  recording is active. Default to no audio capture and no cloud upload.
- Preserve the terminal path when camera preview or browser launch fails.
  Do not make a browser the only way to inspect an uncertain attempt.
- Add an optional, pinned `onboarding-ui` dependency profile and native-helper
  manifest. Retain base simulation without UI or hardware imports. Package
  approved offline wheels/helper/assets and a local troubleshooting guide.
- Doctor checks should report version/backend availability without opening a
  device. A driver installation or Windows privacy setting change is a
  separate user-visible administrative action, not a normal app startup step.

Future command shape, **not currently implemented**:

```powershell
.\rocell.ps1 physical-onboard wizard --mode rehearsal --ui browser
.\rocell.ps1 physical-onboard wizard --session-id <verified-v2-id> --ui browser
```

Extend the current launcher only after these service/CLI contracts exist and
are tested. Existing startup commands must not silently gain device-open
behavior in an update.

## 9. Calibration and connection must join the same data flow

```text
received unit + persistent identity + observed native mode/settings
                          |
           secured optics/support + measured board/tag map
                          |
                 installed camera calibration
                          |
             observed board/station poses and uncertainty
                          |
 arm identity/firmware + measured model/controller correlation + tool TCP
                          |
          target maps -> reviewed trajectory -> bounded executor
                          |
        achieved-state and independent task-outcome observation
```

The camera is fixed relative to the board support, but images can still be
occluded by the arm and tool. The wizard must collect visibility evidence at
later qualified arm poses; it must not assume every tag remains observable.
Loss of required visibility produces a hold or a separately qualified
observation strategy, not a guessed pose. Do not introduce a moving-camera
fallback when static tags are hidden.

Calibration implementation work:

1. Guide camera focus/illumination and target-depth checks before final fixing.
2. Prepare a scale-verified calibration chart and an acquisition plan with
   variation across the field and pose. Precommit development/model-selection
   and untouched acceptance partitions using the existing dataset policy.
3. Acquire retained native samples; derive detector images with known pixel
   transforms. Solve installed intrinsics/distortion and validate residuals
   and coverage on held-out data, not just a single training RMS number.
4. Register the camera to the surveyed board/tag map; check station landmarks
   independently. Record translation, orientation, uncertainty and all
   dependency epochs. Do not estimate a full 3D workcell from one unqualified
   planar homography.
5. Preserve distinct board, keyboard-keytop and phone-screen planes. Keyboard
   height and phone screen height affect pixel-to-contact coordinates.
6. Characterize robot-to-board, tool-tip and controller/model relationships
   through separate qualified reference campaigns. The repository already
   identifies configuration-dependent vendor model/controller FK residuals;
   one rigid offset or reported Cartesian telemetry is not sufficient proof.
7. Simulate exact target/trajectory plans against the current measured
   calibration candidate; evaluate combined localization, mechanics, TCP,
   fixture and execution uncertainty against each target's safe area.
8. Validate empty-cell behavior and noncontact hover before any contact work.
   Retain the existing separate keyboard and Android contact releases.

Connection success is therefore a prerequisite, not a substitute for typing
accuracy. Existing sensitivity simulations already flag stock-phone target
margin problems under sampled assumptions. The interface should report
target-specific limitations and permit a separately reviewed larger-target
Android test screen; it must not label all taps reliable because tags detect.

For keyboard use, later record key layout, physical target centers/heights,
tip compliance/travel and independent registered-keystroke outcomes. A
single-tip actuator must not silently translate unsupported simultaneous
modifier chords into sequential presses. For Android use, later bind device
orientation, screen/UI mapping, touch-capable tool and independent tap result.
ADB or a companion test app may observe outcomes with separate consent; it
must not replace the requested physical tap with software input injection.

completion, exports verifiable evidence and clearly lists physical tests
still due. A changed camera, package, firmware or fixture invalidates the
correct downstream stages.

### P7 — Package and qualify the arrival build

**Maps to:** M11/M12.

Provide one controlled launcher, pinned optional dependencies/native helper,
offline assets/manual, host-doctor output, read-only recovery/export path and
clean-host installation tests. Complete the existing independent reviews,
durability tests, static-primary apply gates and post-apply validation before
the first physical session can begin.

**Exit:** a documented, reproducible pre-hardware release with an honest
verification manifest and a sequenced physical acceptance checklist. No
“hardware-ready” badge based solely on test doubles.

### P8 — Received-hardware acceptance, then later operations console

**Maps to:** physical commissioning stages, followed by separately scoped
runtime/contact development.

Execute the prepared acceptance checklist on the actual camera and arm.
Establish optics, persistent identities, native capture/controls, power/reset
behavior, firmware compatibility and physical calibration. Fix discrepancies
through reviewed profile/provider changes and successor sessions.

Only after the necessary independent reference/noncontact releases should the
separate qualified executor become available in the Operations tab. Individual
keypress and Android tap contact trials start on dummy targets and require
their own acceptance, tool/compliance and independent outcome evidence.

**Exit:** distinguish camera-connected, diagnostic-arm-connected,
noncontact-qualified and contact-qualified capabilities. These are not one
global Connected/Ready checkbox.

## 12. Verification strategy before the hardware arrives

### 12.1 Automated coverage matrix

| Test family | Scenarios | Required observation |
| --- | --- | --- |
| Zero-I/O startup | Imports, constructor, doctor, GET, refresh, session resume | No camera activation, serial open, power instruction or command dispatch |
| Identity | Two identical cameras, missing/duplicate serial, reordered indices, changed COM, removed/replaced device | No first-device fallback; rebind/hold where required |
| Windows adapter | Unsupported control, API failure, native-type conversion, unexpected stride, helper version mismatch | Accurate observed capabilities; no fabricated success |
| Camera settings | Requested/actual mismatch, auto exposure re-enabled, driver coercion, setting drift after reopen | Failed readback or new epoch; downstream evidence invalidated |
| Preview lifecycle | Slow consumer, timeout, tab close, explicit stop, worker hang, source drift | Bounded memory/time, one owner, cleanup recorded, no auto-renew/reopen |
| Frames | Old buffers, rewrapped images, missing sequence, bad timestamp, dropped samples, hidden crop | No false freshness or native calibration pass |
| Data | Full frame above item limit, padding, disk-full, chunk loss, interrupted manifest, quota exhaustion | No partial dataset accepted; no unbounded memory/disk growth |
| Arm serial | Open-time reset, boot chatter, quiet-buffer failure, stale valid packet, malformed/partial reply, short write | Correct write count, preserved bytes, no blind retry or live motion |
| Power lifecycle | Duplicate energize prompt, changed observer/evidence, unknown final off state | Unique envelope per event; uncertainty/quarantine when required |
| Concurrency | Double click, two tabs, two processes, stale request after review | At most one admitted campaign; status reads have no effect |
| Recovery | Worker/app death before/after intent/arming/write/close | Existing attempt inspected; no replay or new-session bypass |
| Calibration | Wrong chart scale, few views, changed focus/support/mode, overlapping holdout data | Candidate rejected or dependencies invalidated |
| Integration | Same simulated cell through UI and terminal | Equivalent canonical actions, receipts and end state |
| Packaging | Clean supported Windows environment, offline assets, missing helper/dependencies | Clear diagnosis; simulation usable without hardware backend |

Use virtual serial/native API fixtures for malformed-data and fault tests; do
not fuzz a physical controller. Tests should compare emitted bytes and device
operation counts, not only final status strings. Extend existing replay/fake
providers where possible and keep simulated provenance impossible to mistake
for retained device evidence.

### 12.2 Performance tests and engineering targets

Record baseline host specifications with each result. Proposed UI targets are
planning targets, not measured guarantees: cached status interactions within
500 ms; prompt visible acknowledgement of a Start/Stop request; no blocking
device I/O on the service event loop. Cleanup deadlines come from worker
contracts, and physical stopping is not a UI-latency metric.

Measure native capture throughput, copy count, encode/hash cost, disk write
rate, preview latency distribution and peak resident memory. Exercise minimum
packed and padded buffers. A bounded native buffer pool and preview queue
must plateau during long synthetic runs. Full-size/GiB dataset tests should be
explicit resource-aware suites, with small structurally equivalent fixtures
in the normal fast tests. Never upscale a low-mode frame to meet a native-mode
dimension assertion.

### 12.3 Evidence labels

Each feature/build report should use three independent fields:

1. Implementation: planned / implemented.
2. Verification: unit-tested / integration-rehearsed / verified-on-received-unit.
3. Authority: unavailable / diagnostic-only / separately qualified capability.

This prevents “implemented” or “tests passed” from being read as permission to
power, move or contact. Hardware test results must include device identity,
host/backend versions, settings, source hash, observations and reviewer.

## 13. Arrival-day acceptance checklist

This is the intended sequence **after implementation and release gates**, not
a procedure authorizing use of the current inactive build.

1. Verify the delivered software package, static-primary build alignment and
   local storage. Launch into zero-I/O status; assign operator/reviewer roles.
2. Inspect the camera package and installation parts. Keep arm actuator power
   disconnected. Bind camera identity and the actual USB topology.
3. Explicitly open the camera through the wizard, read back native mode and
   supported controls, show live imagery, verify cleanup and complete declared
   identity/reopen/freshness trials.
4. Test one-metre focus, field coverage and keytop/screen-depth sharpness.
   Resolve any lens/lighting/height issue before final mounting/calibration.
5. Secure and survey the final static installation. Acquire/assess installed
   calibration and board registration. Record hardware witness marks and
   dependency epochs.
6. Inspect and bind the Pro arm/controller, correct serial USB port, supply,
   cable and firmware evidence plan without opening serial.
7. Complete power-safety review. Perform one observed manual startup with no
   host commands and prove final de-energization.
8. Under a new envelope, run one explicit feedback-only connection campaign;
   close, de-energize and review the complete result/firmware evidence.
9. Conduct the separately authorized reference and empty-cell noncontact
   campaigns; then one-device-at-a-time hover acceptance and accuracy review.
10. Export/verify the diagnostic bundle. Only subsequent independent contact
    qualification enables physical keypresses or Android taps.

Stop at the first failed prerequisite and use the recorded remediation path.
Do not repeatedly power-cycle or open serial to see whether a failure clears.

## 14. Returning-day startup and configuration reuse

The application should remember bindings and reviewed candidates, but never
assume the hardware has not changed:

1. Verify source/package, storage health and prior attempts before session use.
2. Show the last configuration and the evidence that may be reused. Source
   drift or unresolved effects produces read-only review, not auto-repair.
3. After an explicit connection action, re-resolve device identity and read
   back settings within a declared campaign. Revalidate camera view/board
   registration and required freshness evidence.
4. Ask for current fixture/tool/lighting/power observations that cannot be
   measured by software. Show exactly which configuration epoch changed.
5. Use new supervised power/connection authorization as required; an earlier
   good day is not standing permission to energize or initialize.
6. Enable only the independently qualified operations whose current
   prerequisites pass. Never resume a partially executed text or tap sequence.

We can automate comparison, acquisition, checks and next-step selection. We
cannot automatically prove physical fixture retention, power-cut availability,
optical adjustment or safe contact from old calibration files alone.

## 15. Open decisions and bounded defaults

| Open fact/decision | Planning default | How it closes |
| --- | --- | --- |
| Actual camera SKU/lens | B0477/IMX283/nominal 16 mm candidate | Receipt/label inspection |
| Near-focus at intended height | Unproven; early optical gate | Chart images at measured installed distance/depths |
| Camera unit serial/persistent identity | Do not assume present | Observed descriptors and reviewed reconnect/reboot policy |
| Native Windows controls | Capability-driven; unsupported shown unavailable | Native spike plus received driver readback tests |
| Camera USB speed and sustainable native delivery | Require observation; no connector-based inference | Topology/speed evidence and bounded capture benchmark |
| Serial bridge/COM identity | Expected vendor bridge, actual identifiers unknown | PnP evidence and physical controller binding |
| Installed firmware/version observation | Hold until an approved method exists | Received-unit evidence and protocol review |
| Startup/reset/boot mission behavior | Potential motion/reset; never assume inert | Controlled source review and supervised physical observations |
| UI stack | Optional FastAPI/Uvicorn/Jinja, local assets | Version/license/packaging spike and dependency pin review |
| Camera helper | Isolated Windows SDK/Media Foundation executable | Compile/native contract tests and hardware qualification |
| Camera-only physical release path | Must satisfy current stage/activation gates | Explicit reviewed migration if additional capability is needed |
| Remote power or remote operation | Out of initial scope | Separate requested hardware/control/safety design |
| Stock Android target precision | Not guaranteed | Measured per-target accuracy and contact acceptance |

These unknowns do not block developing the contracts, workers, UI and
rehearsals. They do block claiming a working physical connection/calibration
before the corresponding observation exists.
